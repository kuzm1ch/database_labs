# Обговорення / неузгодженості в формулюванні завдання

Файл зібрано з `docs/index.html` (лабораторний опис). Тут лише питання та розбіжності, без змін до оригіналу.

## 1. Різні шляхи API

- У блоці **«Технічні вимоги»** згадані ендпоінти на кшталт `POST /api/sensors`, `DELETE /api/sensors/{code}`, `PUT /api/rules`.
- У **«Промпті №1»** використані префікси `/api/mongo/...` (`GET /api/mongo/config`, `POST /api/mongo/sensors` тощо).

**Питання для викладача:** який набір URL є канонічним для здачі / перевірки?

## 2. Поля документа правил у MongoDB

- У вимогах приклад містить `action_state` (на кшталт `COOLING`).
- У промпті для AI — `active_state` та `normal_state`.

**Питання:** які саме імена полів обов’язкові в колекції `rules`?

## 3. Схема таблиці ScyllaDB

- У вимогах таблиця `sensor_history`: `object_id`, `ts`, `val1`, `val2`, `val3`, `alert_triggered`.
- У промпті до `seed_data.py` додані `device_mac`, `linkquality`, `battery_mv` тощо.

**Питання:** чи достатньо «короткої» схеми з вимог, чи обов’язкові додаткові колонки «як у Zigbee2MQTT»?

## 4. Який сенсор — «головний» для графіка Min/Avg/Max

- У варіантах сказано, що **перший** з трьох базових сенсорів йде на графік №1.
- У схемі Scylla один рядок містить `val1`, `val2`, `val3` без явного мапінгу на коди метрик (`temp`, `humidity` тощо).

**Питання:** як саме студент фіксує відповідність `val1/val2/val3` метрикам варіанта (документ у MongoDB, конвенція, один `object_id` на варіант)?

## 5. Умови тригера (operator)

- У прикладах правил зазвичай `>` або складні умови з «або» (наприклад, температура **або** дим).
- У промпті правило спрощене до одного `metric`, `operator`, `threshold`.

**Питання:** чи достатньо однієї метрики та одного порогу для всіх варіантів, чи для частини варіантів потрібна логіка «АБО/І» між полями?

## 6. Варіанти 7 та 24 (згадка TTL)

- Варіант 24: «в Redis з TTL 5 хв» для стану дозування.
- Решта варіантів про Redis TTL для дашборду не говорять (у вимогах кеш дашборду — **60 с**).

**Питання:** чи другий TTL (5 хв) — окреме обов’язкове правило для цих варіантів, чи це лише приклад формулювання?

## 7. Термін «перший сенсор» у таблиці варіантів

- Порядок колонки «Базові сенсори» визначає «перший» для графіка №1.

**Питання:** чи можна міняти порядок у MongoDB (наприклад, сортування за `code`), чи «першість» задається лише порядком у таблиці варіанта в методичці?

## 8. CQL keyspace у сучасній Scylla (версії на кшталт 2026.x)

- У методичці в прикладі CQL зазвичай `SimpleStrategy`, `replication_factor: 1`.
- На Scylla 2026 з увімкненими **tablets** таке створення keyspace може завершитися помилкою на кшталт `SimpleStrategy doesn't support tablet replication`.

**Питання:** чи оновити приклад у методичці на варіант, сумісний із tablet replication (наприклад NTS + `tablets = {'enabled': false}` або документація Scylla), щоб студенти не застрягали на першому `CREATE KEYSPACE`?
