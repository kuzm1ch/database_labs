Мета

Навчитися обирати базу даних під задачу і побудувати локальний веб-додаток, у якому MongoDB зберігає реєстр сенсорів і правила, Redis тримає поточний стан і кеш, а ScyllaDB накопичує історію вимірів для графіків. Друга частина мети: пройти цей шлях з безкоштовними AI-інструментами, порівняти кілька з них і вміти пояснити, який код вони згенерували і чому він працює саме так.

Кожен студент робить додаток за своїм варіантом зі списку. Об'єкт, сенсори і правило свої, але додаток має закривати базові потреби такого моніторингу:

  • поточний стан сенсорів на екрані;
  • візуалізація історії: графік вимірів за час;
  • пороги (thresholds): задати, змінити і побачити, що сталося, коли значення перетнуло поріг;
  • історія цих подій, а не лише останнє число.

Чому в одній системі використовуються три різні бази даних?

У сучасних IoT та високонавантажених системах одна база даних не може однаково добре вирішувати всі задачі. У цьому проєкті ви будуєте локальний веб-додаток розумного моніторингу, де MongoDB відповідає за гнучкий реєстр обладнання та правил, що редагуються прямо з фронтенду, Redis миттєво віддає поточний стан і кешує важкі розрахунки, а ScyllaDB зберігає тисячі історичних вимірів для побудови агрегаційних графіків.

Чіткий розподіл ролей кожної бази даних

1. Реєстр сенсорів і правил MongoDB

Працює напряму з формами на фронтенді. Зберігає колекцію sensors та правила автоматизації:

  • Гнучка схема (Schema-less): кожен датчик має власні вкладені метадані (specs: точність, зона, батарея, калібрування).
  • Живий CRUD з UI: додавання нового сенсора та зміна порогу тривоги (threshold) прямо з браузера без перезапуску коду.
find() · insert_one() · update_one({$set}) · delete_one()
2. Швидкі стани та Кеш Redis

Працює в оперативній пам'яті (In-Memory) для миттєвої відповіді (<1 мс):

  • Live State (Hash): поточні показники датчиків та прапорець стану реле автоматизації (actuator_status).
  • Query Cache (String + TTL): кешування готових точок агрегаційних графіків зі ScyllaDB на 60 секунд.
HSET / HGETALL · SETEX / GET / TTL / DEL (Cache-Aside)
3. Часові ряди та Аналітика ScyllaDB

Зберігає тисячі сирих історичних записів (Time-Series) кожної хвилини у широких таблицях (Wide-Column):

  • Швидка вибірка історії об'єкта за рахунок Partition Key (object_id) та Clustering Key (ts DESC).
  • Джерело сирих даних для розрахунку агрегаційних дашбордів.
Масовий INSERT · вибірка CQL за діапазоном часу

Як ці три бази взаємодіють між собою на фронтенді?

Сценарій 1 (MongoDB → Фронтенд → Redis): Користувач відкриває сайт і бачить список зареєстрованих датчиків із колекції sensors у MongoDB. Через форму на сайті студент додає новий датчик (наприклад, резервний термометр зі специфічним JSON-полем {"location": "Стеля", "accuracy": "0.1C"}) або змінює поріг спрацювання тривоги (threshold) прямо в інтерфейсі. Зміни миттєво записуються в MongoDB, відображаються на сторінці, а бекенд одразу перевіряє новий поріг і перемикає статус реле в Redis Hash!

Сценарій 2 (ScyllaDB → Агрегація → Кеш у Redis): Фронтенд запитує дані для двох аналітичних графіків за останні 12 годин: (1) Коридор значень Min / Avg / Max по годинах та (2) Гістограма кількості спрацювань тривоги по годинах. При першому запиті бекенд читає 720 сирих записів зі ScyllaDB, агрегує їх по годинах і кладе готовий JSON у Redis на 60 секунд (SETEX). Усі наступні оновлення сторінки віддають графіки з Redis за 1 мс.

Таблиця індивідуальних варіантів (25 студентів)

Кожен студент виконує роботу відповідно до свого номера в списку групи. Три базові сенсори варіанта мають бути зареєстровані як документи в колекції sensors у MongoDB (плюс можливість додати 4-й кастомний сенсор через UI). Перший сенсор агрегується на Графіку №1 (Min/Avg/Max), а порушення порогу тригера (який теж зберігається і редагується в MongoDB) рахується на Графіку №2. Відповідність колонок у ScyllaDB фіксована: val1 — перший сенсор зі списку варіанта, val2 — другий, val3 — третій; цей порядок не змінюється.

Як виглядають реальні дані з IoT-датчиків у промисловості та Smart Home

У реальних проектах датчики ніколи не відправляють просто число 24.5. Вони спілкуються за протоколом MQTT або HTTP і формують структуровані JSON-пакети, які містять апаратну адресу пристрою (ieee_address або MAC), діагностику радіоканалу (linkquality / RSSI), напругу живлення (voltage_mv / battery) та паспорт можливостей сенсора (exposes). Нижче наведені три головні світові стандарти та відкриті датасети, на які слід орієнтуватися при генерації даних у вашому проєкті.

1. Стандарт Zigbee2MQTT (Xiaomi Aqara / Sonoff / Tuya)

MongoDB + Redis

Найпопулярніший відкритий стандарт для бездротових Zigbee-датчиків. Кожен пристрій публікує два типи JSON: паспорт пристрою (Exposes) — ідеально лягає в колекцію sensors у MongoDB, та пакет телеметрії стану — ідеально лягає в Redis Hash та ScyllaDB.

  • Документація Zigbee2MQTT: Приклади JSON-повідомлень
  • Специфікація Exposes (Як описуються характеристики датчиків)
  • Каталог 5800+ реальних датчиків із фото та їхніми JSON-полями

Оптимізований docker-compose.yml

Увага: Конфігурація ScyllaDB спеціально обмежена за допомогою --developer-mode 1, лімітом оперативної пам'яті (1 ГБ) та CPU (1 ядро). Це гарантує безперебійний запуск на звичайних студентських ноутбуках та Windows WSL без повного зависання системи. 

services:
  # 1. MongoDB - Реєстр сенсорів (гнучка схема) та правил автоматизації
  mongodb:
    image: mongo:9.0
    container_name: database_lab_mongo
    ports:
      - "27017:27017"
    volumes:
      - mongo_data:/data/db
    environment:
      MONGO_INITDB_DATABASE: app_db
    restart: always

  # 2. Redis - Рівень миттєвих станів (Hash) та кешування дашбордів (SETEX)
  redis:
    image: redis:8.10-alpine
    container_name: database_lab_redis
    ports:
      - "6379:6379"
    command: redis-server --loglevel warning
    volumes:
      - redis_data:/data
    restart: always

  # 3. ScyllaDB - Сирі часові ряди (Time-Series) для агрегацій
  scylla:
    image: scylladb/scylla:2026.3
    container_name: database_lab_scylla
    ports:
      - "9042:9042"
    # Налаштування для економії ресурсів ноутбуків!
    command: --developer-mode 1 --overprovisioned 1 --smp 1 --memory 1G
    volumes:
      - scylla_data:/var/lib/scylla
    deploy:
      resources:
        limits:
          memory: 1500M
    restart: always

volumes:

  redis_data:
  scylla_data:

Чіткі технічні вимоги до кожної бази даних

Вимога №1 MongoDB

Динамічний реєстр сенсорів та керування порогом тригера з UI

Чому саме MongoDB? Тому що датчики різних моделей мають різний набір паспортних характеристик (Schema-less / Polymorphic Pattern), і ними зручно керувати напряму з фронтенду у форматі JSON.

  • Колекція sensors: зберігає документи всіх датчиків об'єкта. Кожен документ обов'язково має вкладений об'єкт specs із різною структурою для різних датчиків (наприклад: у датчика температури {"model": "DS18B20", "accuracy": "±0.5C", "zone": "Main"}, а у датчика CO2 — {"calibration_date": "2026-01-10", "max_ppm": 5000, "interface": "I2C"}).
  • Додавання та видалення сенсора через фронтенд (POST /api/mongo/sensors, DELETE /api/mongo/sensors/{code}): на веб-сторінці має бути форма «Додати новий сенсор у MongoDB» (назва, код метрики, одиниця виміру, локація/модель). Щойно студент натискає «Додати» — документ зберігається в колекцію sensors і миттєво з'являється у списку обладнання на фронтенді.
  • Редагування правила автоматизації з фронтенду (PUT /api/mongo/rules): у колекції rules зберігається документ активного тригера варіанта (наприклад, {"object_id": "variant_01_smart_flat", "metric": "temp", "operator": ">", "threshold": 26.0, "active_state": "COOLING", "normal_state": "NORMAL"}). Студент має змогу прямо на сайті змінити число threshold — воно оновлюється в MongoDB через $set, і бекенд одразу перераховує стан реле!
Вимога №2 Redis

Миттєві прапорці стану (Hash) та кеш агрегаційного дашборду (SETEX)

  • Швидкий стан об'єкта (Hash device:state): зберігає останні відомі показники всіх сенсорів та поточний прапорець стану виконавчого пристрою (actuator_status — наприклад, NORMAL або COOLING / EMERGENCY_SHUTDOWN). Коли студент змінює поріг у MongoDB або приходить новий вимір, статус у Redis миттєво оновлюється.
  • Кешування агрегованих графіків (String cache:dashboard:analytics з TTL 60 сек): реалізує патерн Cache-Aside. Розраховані зі ScyllaDB точки двох графіків зберігаються у Redis на 60 секунд. На UI обов'язково виводиться бейдж статусу кешу (REDIS_CACHE_HIT із таймером TTL або SCYLLADB_AGGREGATED_MISS) та кнопка «Скинути кеш Redis».
Вимога №3 ScyllaDB

Сирі часові ряди та два агрегаційні графіки на дашборді

  • Таблиця часових рядів у ScyllaDB: схему дозволено розширювати, але обов'язковий мінімум — по одній колонці значення на кожен із трьох базових сенсорів варіанта (таблиця з однією-двома колонками метрик не зараховується): 
    -- ScyllaDB 2026.x: SimpleStrategy не підтримує tablet replication,
-- тому NetworkTopologyStrategy + tablets вимкнено
CREATE KEYSPACE IF NOT EXISTS smart_monitoring
  WITH replication = {'class': 'NetworkTopologyStrategy', 'datacenter1': 1}
  AND tablets = {'enabled': false};

CREATE TABLE IF NOT EXISTS smart_monitoring.sensor_history (
  object_id text, ts timestamp,

Я розробляю локальний навчальний проєкт на Python (FastAPI) з трьома NoSQL базами даних:
1. MongoDB (`mongodb://localhost:27017`, база `app_db`)
2. Redis (`localhost:6379`, decode_responses=True)
3. ScyllaDB (`localhost:9042`, keyspace `smart_monitoring`)

Напиши мені два файли: `seed_data.py` та `main.py`.

У файлі `seed_data.py`:
1. У MongoDB створює:
   - Колекцію `sensors` (за стандартом Zigbee2MQTT Exposes / Tasmota): додає 3 документи моїх базових сенсорів, де кожен документ має `code`, `ieee_address` (наприклад, `"0x00158d00045b2c91"`), `vendor` (наприклад, `"Aqara"`, `"Sonoff"`, `"Sensirion"`), `model` (наприклад, `"WSDCGQ11LM"`, `"SCD41"`), `unit` та вкладений об'єкт `specs` із різними полями (`value_min`, `value_max`, `accuracy`, `interface`, `calibration_date`, `mount_zone`).
   - Колекцію `rules`: зберігає документ правила автоматизації `{"object_name": "...", "object_id": "...", "metric": "...", "operator": ">", "threshold": ..., "active_state": "...", "normal_state": "NORMAL"}` (`object_id` — той самий ідентифікатор об'єкта, що й у таблиці `sensor_history` у ScyllaDB).
2. У ScyllaDB створює keyspace `smart_monitoring` (для ScyllaDB 2026.x: `NetworkTopologyStrategy` з `tablets = {'enabled': false}`, бо `SimpleStrategy` падає з помилкою tablet replication) та таблицю `sensor_history (object_id text, ts timestamp, val1 double, val2 double, val3 double, alert_triggered int, PRIMARY KEY (object_id, ts)) WITH CLUSTERING ORDER BY (ts DESC)`, де `val1`, `val2`, `val3` — відповідно перший, другий і третій сенсори мого варіанта (мінімум — 3 колонки метрик; за бажанням додай телеметрію `device_mac`, `linkquality`, `battery_mv`). Генерує 720 історичних записів за останні 12 годин (крок 1 хвилина) із реалістичними коливаннями та періодичними піками, де спрацьовує поріг (`alert_triggered = 1`); якщо додані колонки телеметрії — заповнює й їх (`linkquality` 110..255 LQI, `battery_mv` 2850..3100 mV).
3. У Redis записує поточні значення сенсорів, а також діагностику телеметрії (`linkquality`, `battery_mv`, `rssi_dbm`, `actuator_status`) у Hash `device:state`.

У файлі `main.py` (FastAPI):
1. `GET "/"` — віддає файл `index.html`.
2. Робота з MongoDB (відображення та керування з фронтенду):
   - `GET "/api/mongo/config"` — повертає список усіх сенсорів із колекції `sensors` та поточне правило з колекції `rules`.
   - `POST "/api/mongo/sensors"` — додає новий сенсор у колекцію `sensors` (приймає `code`, `name`, `unit` та довільний об'єкт `specs`), а також ініціалізує для нього початкове значення в Redis Hash `device:state`.
   - `DELETE "/api/mongo/sensors/{code}"` — видаляє сенсор із колекції `sensors`.
   - `PUT "/api/mongo/rules"` — оновлює значення порогу `threshold` у колекції `rules` в MongoDB, після чого одразу перевіряє поточне значення датчика в Redis Hash `device:state` і автоматично перемикає `actuator_status` у Redis!
3. Робота з Redis Live State:
   - `GET "/api/redis/state"` — миттєво повертає всі поля з Redis Hash `device:state`.
   - `POST "/api/redis/simulate-tick"` — генерує новий поточний вимір, звіряє його з актуальним порогом із MongoDB, оновлює Redis Hash `device:state` і додає рядок у ScyllaDB.
4. Робота зі ScyllaDB та Кешем Дашборду (Cache-Aside):
   - `GET "/api/analytics"` — перевіряє ключ `cache:dashboard:analytics` у Redis. Якщо ключ є — повертає JSON із `"source": "REDIS_CACHE_HIT"` та поточним `"ttl"`. Якщо немає (Cache MISS) — вибирає дані зі ScyllaDB за останні 12 годин, групує їх по годинах (12 точок) і обчислює для кожної години: `min_val`, `avg_val`, `max_val` першого датчика та `alerts_count` (суму `alert_triggered`). Зберігає результат у Redis через `SETEX` на 60 секунд і повертає з `"source": "SCYLLADB_AGGREGATED_MISS"`.
   - `POST "/api/cache/clear"` — видаляє ключ `cache:dashboard:analytics` із Redis.

  3. Додайте у ~/.codex/config.toml:
model = "openai/gpt-oss-120b"
model_provider = "groq"

[model_providers.groq]
name = "Groq"
base_url = "https://api.groq.com/openai/v1"
env_key = "GROQ_API_KEY"
wire_api = "responses"

Запуск: codex у папці проєкту. Формат конфігу може змінюватись між версіями, звіряйтесь з документацією Groq.

  • Тримайте в корені PROJECT_CONTEXT.md: номер варіанта, сенсори, тригер, структура папок, що вже працює, що далі, відомі помилки. Новий інструмент прочитає його і не проситиме пояснювати все з нуля.
